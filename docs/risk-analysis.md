# 예상문제 및 해결방법

| 구분 | 문제점 | 해결방안 |
|------|--------|----------|
| 개발 측면 | Knowledge Graph 기반 설정 충돌 감지 시스템은 LLM의 관계 추론 정확도, GraphRAG 하이브리드 검색 성능, Kafka 기반 Ripple Effect 비동기 역추적, Vector DB·Graph DB 이중 저장 정합성 등 복수의 고난도 기술 요소가 유기적으로 결합되어야 하는 구조로, 단일 레이어의 기술 미완성이 전체 서비스 품질에 연쇄적으로 영향을 미침 | LangGraph 에이전트 파이프라인으로 LLM 추론·Self-Validation 단계를 분리하고, Elasticsearch와 Graph DB를 연계한 하이브리드 검색으로 속도·정확도를 확보. Kafka EDA로 역추적 부하를 비동기 분산 처리하며, DDD 컨텍스트 경계 설계와 정합성 검증 배치로 이중 저장 구조의 안정성을 유지 |
| 프로젝트 관리 측면 | PoC 단계에서 LLM 텍스트 → Graph DB 변환 및 RAG retrieval 핵심 로직의 기술 검증이 지연될 경우 MVP 전체 일정이 연쇄 지연되며, GraphRAG·LangGraph 등 신규 기술 스택에 대한 러닝커브가 병목으로 작용할 수 있음 | PoC를 개발 착수 전(6~7월)에 조기 배치하고, 기술 난이도가 높은 항목을 Sprint 초반에 선검증해 리스크를 조기 식별. 검증 실패 시 멘토 지원 요청 또는 대안 기술 스택으로 신속 전환 |
| 상용화 측면 | 장편 연재 작가라는 틈새 시장 특성상 초기 사용자 확보와 서비스 인지도 제고가 어려우며, LLM API 사용 비용이 사용량에 비례해 증가해 고연산 기능(Ripple Effect 역추적, 대형 프로젝트 분석) 중심의 운영 수익성 확보가 어려울 수 있음 | 웹소설 작가 커뮤니티와 연재 플랫폼 채널을 중심으로 무료 기본 티어로 초기 사용자 풀을 확보하고, 고연산 기능은 프리미엄 구독 모델로 전환해 API 비용을 회수. 프롬프트 최적화·캐싱으로 불필요한 호출을 최소화 |
| 기타 | 작가가 업로드하는 미공개 원고의 저작권 귀속 문제 및 LLM 학습 데이터 활용 여부에 대한 법적 분쟁 가능성. 원고 유출 시 서비스 신뢰도에 치명적 타격 우려 | LLM API 호출 시 Zero Data Retention 정책을 적용해 업로드된 원고가 모델 학습에 활용되지 않음을 보장하고, 분석 완료 후 원고 원본을 즉시 삭제하는 정책을 수립. 저장이 필요한 경우의 암호화 보관은 추후 검토 단계로 처리하며, 데이터 처리 방침을 온보딩 단계에서 명확히 고지 |
| 기타 | Claude 등 외부 LLM API의 정책 변경·비용 인상·서비스 중단 시 Knowledge Graph 구축 및 설정 충돌 감지 등 핵심 기능 전체가 중단될 위험 | 단기적으로는 다중 LLM 공급사(Claude, OpenAI 등) 연동 구조와 LangGraph 에이전트 레이어의 fallback 처리 로직을 구현해 특정 공급사 장애에 즉시 대응한다. 중장기적으로는 Ollama 기반 로컬 LLM을 자체 호스팅해 외부 API 의존도를 단계적으로 축소하고, 데이터 보안 측면의 이점도 함께 확보한다 |

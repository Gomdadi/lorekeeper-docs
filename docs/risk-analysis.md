# 예상문제 및 해결방법

| 구분 | 문제점 | 해결방안 |
|------|--------|----------|
| 개발 측면 | LLM이 원고에서 인물·사건·관계를 추론할 때 오탐(잘못된 인과관계 추출)이 발생해 Knowledge Graph의 정확도가 낮아질 수 있음. 특히 화자 전환이 잦거나 복선이 깔린 문장에서 관계 추론 실패 가능성이 높음 | 프롬프트 엔지니어링을 반복 개선하고, 추출 결과에 대한 Self-Validation 단계를 추가해 신뢰도 낮은 항목은 작가 검토를 요청하는 방식으로 보완. 정탐/오탐 피드백 데이터를 수집해 Graph 탐색 로직을 지속 개선 |
| 개발 측면 | GraphRAG 기반 설정 오류 탐지 시 Graph DB 반복 쿼리로 인한 응답 지연이 발생해 사용자 경험이 저하될 수 있음. 연재 회차가 쌓일수록 쿼리 대상 노드·엣지 수가 급증해 성능 저하가 심화될 우려가 있음 | Elasticsearch를 통한 키워드·요약 검색과 Graph DB 기반 인과관계 탐색을 분리하는 하이브리드 검색 구조로 속도와 정확도를 동시에 확보. 쿼리 최적화 및 캐싱 전략을 적용하고, 탐지 결과는 비동기 처리 후 알림으로 전달 |
| 개발 측면 | Ripple Effect 역추적 시 연관 에피소드가 많을수록 Kafka 파이프라인의 처리 부하가 급증해 시스템 불안정 우려. 동기식 처리 시 WAS가 응답 불능 상태에 빠질 수 있음 | Kafka 기반 EDA(Event-Driven Architecture)로 비동기 분산 처리를 수행해 WAS 부하를 분리. 처리 단위를 제한하고, 영향 범위가 큰 경우 작업을 분할 처리하며 진행 상태를 실시간으로 사용자에게 노출 |
| 개발 측면 | Vector DB(임베딩 청크)와 Graph DB(Cypher 기반 지식 그래프)를 병행 운용하는 이중 저장 구조에서, 원고 수정·삭제 시 두 DB 간 데이터 정합성 유지가 어려울 수 있음 | 원고 수정·삭제 이벤트 발생 시 두 DB를 동시에 업데이트하는 트랜잭션 처리 로직을 설계하고, DDD 구조에서 '원고 컨텍스트'와 '검증/추적 컨텍스트'를 철저히 분리해 결합도를 낮춤. 정합성 검증 배치 작업을 주기적으로 실행 |
| 프로젝트 관리 측면 | PoC 검증 지연 또는 GraphRAG·LangGraph 등 핵심 기술 학습 부담으로 인해 MVP 개발 일정이 지연될 위험. 새로운 기술 스택에 대한 러닝커브가 병목으로 작용할 수 있음 | Sprint별 완료 기준을 사전 합의하고, PoC 단계에서 기술 난이도가 높은 항목(LLM 텍스트 → Graph DB 변환, RAG retrieval 핵심 로직)을 조기에 선검증해 기술 리스크를 최소화. 난이도 초과 시 멘토 지원 요청 또는 대안 기술 스택 전환 |
| 프로젝트 관리 측면 | 3인 팀에서 Backend·Frontend·Infra·AI 파이프라인 역할이 혼재되어 병목이 발생하거나 커뮤니케이션 오버헤드가 커질 수 있음 | 역할 분담과 Git Branch 전략을 명확히 정의하고, 데일리 스크럼과 주간 회고를 통해 병목 구간을 조기에 발견해 우선순위를 재조정. DDD 컨텍스트 경계에 따라 개발 영역을 분리해 독립적인 작업이 가능하도록 구조 설계 |
| 프로젝트 관리 측면 | MVP 범위가 확장되어 핵심 기능(설정 충돌 탐지) 완성도보다 기능 수를 늘리는 방향으로 흐를 수 있음. 템플릿 마켓·플롯 추천 등 포스트 MVP 기능이 MVP 단계에 혼입될 위험 | Product Backlog 우선순위를 Sprint마다 재검토하고, MVP 핵심 기능(Phase 1 Ingestion + Phase 2 Detection)에만 집중. 포스트 MVP 확장 기능은 별도 백로그로 분리해 관리 |
| 상용화 측면 | 장편 연재 작가라는 틈새 시장 특성상 초기 사용자 확보가 어렵고 서비스 인지도가 낮을 수 있음. 국내 유사 서비스(노벨라 등) 사용자를 전환시키는 데 마케팅 비용이 클 수 있음 | 웹소설 작가 커뮤니티(문피아, 조아라 작가 포럼 등)와 카카오페이지·네이버시리즈 연재 작가 채널을 중심으로 베타 테스터를 모집. 무료 기본 티어로 초기 사용자 풀을 확보하고 실사용 후기를 통한 입소문 유도 |
| 상용화 측면 | LLM API(Claude 등) 사용 비용이 사용량에 비례해 증가해 운영 수익성을 확보하기 어려울 수 있음. 특히 장편 원고 전체 분석·Ripple Effect 역추적 등 고연산 기능은 API 호출 비용이 높음 | 원고 분석 요청 빈도에 따라 요금제를 차등 적용하고, 프롬프트 최적화와 캐싱으로 불필요한 API 호출 최소화. 고연산 기능(레트콘 역추적·대형 프로젝트 관리)은 프리미엄 구독 모델로 전환해 비용 회수. 장기적으로 경량 모델 도입 검토 |
| 기타 | 작가가 업로드하는 원고의 저작권 귀속 문제 및 LLM 학습 데이터 활용 여부에 대한 법적 분쟁 가능성. 미공개 원고 유출 시 작가의 신뢰도와 서비스 평판에 치명적인 타격 우려 | 서비스 이용약관에 원고 데이터의 용도(분석 전용, 학습 미활용)를 명시하고, 업로드된 원고를 분석 완료 후 즉시 삭제하거나 암호화 보관하는 정책 수립. 데이터 처리 방침을 온보딩 단계에서 명확히 고지. LLM API 호출 시 원고 데이터가 모델 학습에 사용되지 않도록 Zero Data Retention 정책 적용도 검토 중 |
| 기타 | Claude 등 외부 LLM API의 정책 변경이나 서비스 중단 시 Knowledge Graph 구축 및 설정 오류 탐지 등 핵심 기능이 중단될 위험 | 특정 LLM 공급사에 대한 의존도를 낮추기 위해 다중 LLM 공급사 연동 구조(Claude, OpenAI 등)를 설계하고, LangGraph 에이전트 레이어에서 fallback 처리 로직을 사전에 구현. 로컬 LLM(Ollama 등)의 처리 성능 검증 후 도입도 검토 중 |
